# 不花钱怎么分发（Windows）

**结论先说**：代码签名不是必需的。对开源工具来说，**不签名直接发是最常见的选择**，
它的代价不是"不能用"，而是"一部分用户第一次打开时要多点一次"。

---

## 1. 不签名会发生什么

用户双击一个从网上下载的、没签名的 exe，Windows 会弹：

> **Windows 已保护你的电脑**
> Microsoft Defender SmartScreen 阻止了无法识别的应用启动。

下面有「更多信息」→「仍要运行」。**点了就能用。** 这是下载量少的新应用都会遇到的，
攒够下载量/信誉以后提示会自动消失。

要写进 README 的就是这一段 —— 大部分用户卡在"不敢点"，不是"点不了"。

### 唯一的例外：Smart App Control 强制开启的机器

SAC 强制开启时，未签名程序是**直接拦、没有「仍要运行」**。这台开发机就是这种状态
（`VerifiedAndReputablePolicyState = 1`）。这类用户只有两条路：用源码跑，或者关掉 SAC
（一次性、不可逆）。

SAC 目前只在部分 Windows 11 全新安装上是开着的，属于少数情况，但 README 里要提一句，
否则收到 issue 会一头雾水。

---

## 2. 三条不用花钱的路（按成本从低到高）

| 方案 | 成本 | 用户体验 | 什么时候用 |
|---|---|---|---|
| **A. 直接发未签名包** | 0 | 首次要「更多信息 → 仍要运行」 | **现在就走这条** |
| **B. 源码分发** | 0 | 要装 Node/pwsh，`npm start` | 给开发者用户；也是 SAC 机器唯一的自助出路 |
| **C. 免费/廉价 OSS 签名** | €0–50/年 | 干净，没提示 | 等真有人抱怨了再上 |

**建议：A + B 同时提供。** 普通用户下安装包，开发者 clone 源码。两者共用同一份代码，
不需要额外维护分支。

## 3. C 的那几个具体渠道（备查，现在不用做）

| 渠道 | 价格 | 说明 |
|---|---|---|
| **SignPath Foundation** | 免费 | 专给开源项目做代码签名（需要项目公开、许可证合规、能走他们的 CI）。最值得先试 |
| **Certum Open Source Code Signing** | 约 €50/年 | 面向开源的廉价证书，比商业证书便宜一个数量级 |
| **Azure Trusted Signing** | 约 $10/月 | 按月的托管签名服务，个人可用（需要身份/组织验证） |
| 商业 EV 证书 | $200–400/年 | **不值得**，只为这个桌宠付这个钱 |
| 自签名证书 | 免费 | ❌ 不推荐：用户得手动把证书装进"受信任的根"，比不签名更麻烦，而且**过不了 SAC** |

## 4. 不签名也能做、而且该做的事

签名解决的是"系统信不信你"，下面这些解决的是"用户敢不敢用"，成本都是 0：

- **发 SHA-256 校验值**，README 里给一行 `Get-FileHash` 命令 —— 用户至少能确认包没被换过
- **发源码包**（GitHub 的 "Source code (zip)" 是自动带的），给一条从源码构建的命令
- **把构建做成可复现的**：写清楚 `npm ci` → `npm run dist`，让愿意的人自己构建
- **首次运行的说明放在下载页最显眼的地方**，别藏在 FAQ 里
- **别改安装包文件名**：SmartScreen 的提示文案会提到文件名，用户截图发 issue 时能对上

## 5. 什么时候重新考虑签名

出现下面任一情况再花钱：

- 有非开发者用户明确说"被拦了不敢装"，且解释之后仍然劝退
- 想做**自动更新**（更新包被拦会让更新流程直接崩，这个理由比首次安装更硬）
- 想上 Microsoft Store

在那之前，把钱留着。顺带一提，**自动更新是唯一一个"不签名就真的做不了"的功能** ——
如果以后要做，那时再评估 SignPath。

## 6. 打包（已配好，`npm run dist` / `npm run pack`）

用 `electron-builder` 出 NSIS 安装包：

```bash
npm run dist     # electron-builder --win nsis  → dist/<产品名> Setup x.y.z.exe
npm run pack     # 只出便携目录      → dist/win-unpacked/
```

注意 Electron 版本钉在 `^28`（33 在这台机器上崩，见 README）。

### 在这台开发机上实测的两件事

1. **便携版能产出**：`npm run pack` 成功，结果是 `dist/win-unpacked/`（约 168 MB 主程序 +
   完整运行时）。这就是可以直接压缩分发的形态。
2. **装不到这台机器上**，两个原因层层叠加：
   - `npm run dist`（NSIS）最后一步会**执行一次刚生成的安装器**来产出卸载程序，
     而那个 exe 是新的、未签名的 → 被本机的应用程序控制策略拦下（exit 2）。
   - 直接运行便携版主程序也是一样：**「应用程序控制策略已阻止此文件」**。

   所以在这台机器上**验证不了打包产物**。dev 模式（`npm start`）不受影响，因为那用的是
   npm 装下来的、原地未改动的 `electron.exe`。

   > 顺带记一笔没查清的：同样是未签名，npm 那份 `electron.exe` 原地能跑，
   > **复制到别处就被拦**；本地用 csc 编的 WinForms exe 又能跑。规则不是"有没有签名"这么简单，
   > 具体判据没钉死（试了签名对比、路径对比、复制对比，结论互相矛盾）。
   > 这不影响开发（dev 模式正常），留作已知问题。

**结论**：要出正式安装包，找一台没开 Smart App Control / 应用控制策略的机器跑 `npm run dist`；
或者按 §2 的方案先发便携版压缩包。
